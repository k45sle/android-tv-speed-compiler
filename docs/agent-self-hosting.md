# Agent self-hosting runbook

Use this runbook when an agent is asked to deploy, troubleshoot, upgrade, or recover this service on a user's Docker host. Keep one service process on one host with its existing data volume and ADB keys. Do not expose the dashboard or ADB daemon publicly, use privileged mode, or add replicas/workers. Preserve each TV's current ADB network mode unless the owner chooses a change. The service does not switch TV modes or install a companion app; see [Wireless debugging and ADB](wireless-debugging-recovery.md) for the owner-selected method and its tradeoffs.

## 1. Inspect before choosing a deployment

1. Confirm the host architecture (`amd64` or `arm64`), Docker Engine/Desktop, Compose v2, network/firewall access to the TV, and whether this is Docker Desktop or a Linux Docker host. **Done when** the host type, architecture, and whether mDNS is needed are known.
2. Clone the public source repository from GitHub. If GitHub asks you to sign in, use the account or credential helper you normally use. Never place a personal access token in a clone URL, command history, checked-in file, or agent chat. Inspect the intended revision and relevant Compose/Dockerfile changes. **Done when** the source checkout and intended revision are identified.
3. Find running and stopped containers for Compose service `android-tv-speed-compiler` with `docker ps -a --filter label=com.docker.compose.service=android-tv-speed-compiler --format '{{.ID}} {{.Names}} {{.Status}}'`. For candidate IDs, inspect only labels and mount/runtime fields, for example `docker inspect -f '{{index .Config.Labels "com.docker.compose.project"}} {{index .Config.Labels "com.docker.compose.project.config_files"}} {{index .Config.Labels "com.docker.compose.project.working_dir"}} {{.Config.User}} {{json .Mounts}}' <container-id>`. The `project.config_files` label may encode multiple ordered files: preserve each exact absolute path and its order. Check volume labels/metadata and list only expected paths in the mounted data directory; never dump `.Config.Env`, full config, or database contents because a bootstrap secret may be supplied through the environment. **Done when** the existing deployment's project, ordered Compose files, working directory, service, and mounted volume are identified, with existing state/auth databases and ADB home presence checked where applicable, or inspection establishes no deployment/data to preserve.
4. Reuse the exact existing project name, ordered Compose files, and named volume. Do not create a second project or an empty replacement volume to work around a failed start. If those identities cannot be established, stop and ask the owner to identify the intended deployment. **Done when** the target identity is recorded without exposing secret contents.

For all commands below, run from the checked-out repository directory and use this shell convention:

```sh
export COMPOSE_PROJECT_NAME='<exact inspected project name>'
export COMPOSE_FILE='<exact inspected compose file>'
dc() { docker compose -p "$COMPOSE_PROJECT_NAME" -f "$COMPOSE_FILE" "$@"; }
```

These commands assume a POSIX shell (Linux/macOS or Git Bash on Windows). In PowerShell, set the same two Compose values and pass them with `docker compose -p <project> -f <file>` for each command; do not run the POSIX function definition there.

For an existing deployment with several Compose files, do not pass the comma-separated label value as one `-f` filename. Replace `dc()` with a function that repeats `-f` once for each inspected absolute path in the original order, for example `dc() { docker compose -p "$COMPOSE_PROJECT_NAME" -f "/path/base.yaml" -f "/path/override.yaml" "$@"; }`. Preserve intentional proxy/network overrides. Use exactly one standalone project file, `compose.yaml` or `compose.linux-host.yaml`; never combine those two variants. Retain the existing network mode unless the owner selected a networking change.

For a new installation only, choose `COMPOSE_PROJECT_NAME=android-tv-speed-compiler` and `COMPOSE_FILE=compose.yaml`. For an existing deployment, substitute its inspected values. `compose.linux-host.yaml` is itself a standalone variant. **Done when** `dc config --quiet` succeeds, the new bundled configuration lists only `android-tv-speed-compiler`, and `dc config --volumes` includes `tvcompiler-data`. For an existing deployment, the service list must include `android-tv-speed-compiler` and only the already inspected intended extra services; verify the app's existing volume mapping and exact physical volume name rather than requiring the bare bundled layout.

## 2. Select the network mode

- **Linux host needing mDNS:** use standalone `compose.linux-host.yaml`. It uses host networking and binds the UI to `127.0.0.1:8000` from inside the host network namespace. Apply a host firewall policy that allows only the intended local UI and trusted TV network access; host networking has no Compose port boundary.
- **Docker Desktop on macOS/Windows:** use `compose.yaml`, which bridges the container and publishes only `127.0.0.1:8000`. Desktop VM networking may not pass mDNS; manual entry of the TV's current IP and the separate pairing and connection ports is the supported fallback. Do not merge the two Compose files.

If the dashboard needs access from another machine, set `LOGIN_ENABLE=true` before changing the bind or adding a proxy. Set `TVCOMPILER_LOCAL_SETUP=0` for remote or proxied access, then follow the HTTPS reverse-proxy, exact public-origin, secure-cookie, and firewall requirements in [operations security settings](operations.md#security-controls-and-limits). A proxy in a sibling container cannot reach the service at its own `localhost`: configure a reachable shared Docker network/service address or a deliberate host-gateway route, then restrict ingress. Keep Uvicorn proxy-header trust disabled. Login-disabled mode is for the bundled loopback-only bind; Host and proxy-header checks cannot prove that every network path is private. **Done when** the selected network mode and any proxy route have been confirmed without publishing the UI or ADB daemon to the public internet.

## 3. Build and validate the selected deployment

1. Let Docker build for the host's native architecture from the source directory. The Dockerfile installs Debian's `adb` package for that architecture and installs locked Python dependencies. Do not force an x86-only Google platform-tools binary onto ARM64. **Done when** `dc build android-tv-speed-compiler` exits successfully for the native host architecture.
2. Validate without printing interpolated values: run `dc config --quiet`, `dc config --services`, and `dc config --volumes`. Compare only the selected Compose file's project/service, volume, loopback binding (or Linux host bind), security options, and environment variable names/settings needed for this deployment. `LOGIN_ENABLE` defaults to `false`; leave it off only with direct loopback access. With login disabled, do not create or reset an account, retrieve a bootstrap token, or change existing auth database contents. When login is enabled, keep the auto-generated bootstrap-token configuration empty unless the owner has deliberately provisioned a 32–256 character secret through a secret mechanism. **Done when** validation succeeds and resolved resource names match the inspected target; no rendered configuration or environment values are exposed.

## 4. Start offline and verify persistence

1. Start only the service with `dc up -d android-tv-speed-compiler`. No TV needs to be connected for first start. **Done when** Compose reports the service running and its health check becomes healthy.
2. Probe health and runtime data permissions without printing secrets:

   ```sh
   dc exec -T android-tv-speed-compiler python -c 'import urllib.request; r=urllib.request.urlopen("http://127.0.0.1:8000/health", timeout=2); print("health_status=" + str(r.status))'
   dc exec -T android-tv-speed-compiler python -c 'import os,tempfile; assert os.getuid()==10001 and os.getgid()==10001; f=tempfile.TemporaryFile(dir="/data/instance"); f.close(); print("uid=10001 gid=10001 instance_writable=yes")'
   ```

   Also inspect container state, redacted logs, configured user, mount, and volume ownership using filtered fields. Health proves the web process responds; it does not prove ADB discovery, TV pairing, or command reachability. The process must run as UID/GID `10001:10001`, with the intended persistent volume mounted at `/data` and writable by that unprivileged user. Do not fix ownership by running the service as root. **Done when** the first probe reports HTTP 200, the second exits successfully with the exact UID/GID and writable marker, and no replacement volume was created.
3. Login is off by default. In that mode, the dashboard opens without an account; anyone who can reach it can control the service and its TVs. The app creates no auth database or bootstrap token. Keep this mode on the bundled loopback-only bind, and retain the same-origin `Origin` plus CSRF cookie/header checks on mutations. When `LOGIN_ENABLE=true`, reuse the existing account if one is configured; toggling the setting does not delete or reset account data. For a new account on the bundled loopback Compose setup, `TVCOMPILER_LOCAL_SETUP=1` permits password-only setup with a unique password of at least 6 characters. For other setup paths, the owner must provide the one-time token and choose a password of at least 6 characters. The token may be retrieved through a private local terminal (`dc exec -T android-tv-speed-compiler cat /data/instance/bootstrap.token`) or provided through the configured secret channel. The agent must not run that command, receive its output, or place the token in chat, logs, Git, command transcripts, or screenshots. A generated token is one-time and removed after successful setup. For an existing deployment, do not reset auth state as part of setup or upgrade. **Done when** the owner confirms the intended login mode works, without disclosing credentials; in login-disabled mode, confirm the dashboard opens and makes no account/token changes.
4. For a new installation, confirm monitoring starts paused. **Done when** the dashboard reports “Monitoring paused”; do not resume it during unattended setup. For an existing deployment, preserve its saved monitoring choice across restart or upgrade and do not change it as part of deployment.

## 5. Pair and validate with the owner

Use these steps only for a new TV/app onboarding or an owner-requested re-pair, connection-method change, or reselection. For restart, upgrade, or restore of an existing instance, preserve its pairing records, saved connection method and endpoint, watched fingerprints and baselines, app selections, and monitoring setting. Verify current reachability and report stale/offline endpoints; do not rewatch, rebaseline, forget, re-pair, or change a TV's network mode as routine deployment work. **Done when** existing state is retained and reachability is checked without changing it, or the owner has explicitly requested onboarding, re-pair, method change, or reselection.

1. For new onboarding or owner-requested re-pair or method change, ask the owner which TV connection method to use. Explain the encrypted Wireless debugging and unencrypted fixed-port TCP/IP options, then follow the matching branch in [Wireless debugging and ADB](wireless-debugging-recovery.md#choose-a-connection-method). Choosing fixed-port TCP/IP does not authorize a third-party companion app. Ask separately before giving companion installation/setup steps. The owner enables the selected mode on the TV. The service does not switch modes or install apps. **Done when** the owner has enabled the selected method on the intended TV and its connection method is recorded in the dashboard.
2. For Wireless debugging, the owner reads the separate pairing IP:port and short code from **Pair device with pairing code** and enters them directly in the dashboard. The service pairing code must stay in the UI; the agent must not ask the owner to send it in chat or receive/store it. The saved pairing keys authorize the service's ADB client. For fixed-port TCP/IP, enter the TV address and port in the dashboard and have the owner approve this service's RSA authorization prompt. Any companion app has its own ADB key and does not authorize the service. A saved method label is configuration metadata, not proof that the live transport is encrypted. **Done when** the dashboard reports the intended TV connected with the expected saved method and identity.
3. On Docker Desktop, enter the current endpoints manually if discovery fails. On Linux host networking, try **Find TVs** when multicast is enabled and have the owner explicitly select each discovered endpoint. Discovery success is not proof that pairing or later reconnection works. **Done when** the dashboard reports the paired TV online, or a clear network/authorization limitation is handed to the owner without changing TV network mode.
3. For new onboarding, the owner can select apps in the wizard; saving each watched app records its current installation as baseline with `initial_compile: false`, so selection itself queues no compile. For owner-requested reselection on an existing TV, open **Manage watched apps**, load the fresh inventory, then change the app checkboxes. Enabling a previously unwatched app records its current installation as the new baseline; disabling an app removes it from the watched allowlist. **Done when** the chosen app allowlist is visible and the owner has confirmed its baseline.
4. Explain that TV reachability/identity, awake/playback safety checks, and current endpoint may affect jobs. On review, both automatic monitoring and the first speed compile start checked; the owner can clear either choice. Monitoring applies globally, and Finish preserves monitoring that is already enabled. A checked compile option queues one job per selected app fingerprint; jobs wait for a confirmed idle TV and any configured maintenance window. Busy TVs or a closed window defer work. Do not automatically toggle monitoring on an existing deployment; follow the owner's explicit choice for requested onboarding. Scheduling retains its saved defaults under **Advanced settings**. A manual compile's foreground override remains an explicit per-job choice. **Done when** the owner has confirmed the monitoring and compile choices and has a clear readiness status.

## 6. Troubleshoot, upgrade, or recover

- **Unhealthy container or failed start:** collect redacted `dc ps`, `dc logs --tail=100 android-tv-speed-compiler`, health, mount, and ownership details. Preserve the project name and volume while correcting the cause. Never include tokens/passwords/pairing codes or replace a populated volume with an empty one. **Done when** the cause is fixed and the service is healthy, or the owner receives exact evidence and the unresolved blocker.
- **Endpoint, authorization, or identity issue:** follow the reconnect and identity procedure in [operations identity and reconnect](operations.md#identity-and-reconnect). Use the TV's current separate TLS pairing and connection ports. If identity verification fails, confirm the intended physical TV with the owner before forgetting and pairing it again. **Done when** the same intended TV reconnects, or its changed identity is explicitly confirmed before re-pairing.
- **Upgrade:** review/fetch the intended source revision, take a complete backup as described in [operations backup and restore](operations.md#stop-backup-restore), then run `dc build android-tv-speed-compiler` and `dc up -d android-tv-speed-compiler` using the same project name, Compose file, and volume. **Done when** the upgraded service is healthy and the existing account, TV records, app selections, history, and ADB keys remain available.
- **Restore:** stop with `dc stop android-tv-speed-compiler`, restore the complete protected volume snapshot to the same named volume, then run `dc up -d android-tv-speed-compiler`. Do not restore only SQLite while discarding its matching ADB keys. **Done when** service health and persisted state are checked and any required re-pairing is reported.
- **Forgotten password:** first confirm login is enabled and the owner requested a reset. If login is disabled, leave auth state alone. Otherwise follow [operations password reset](operations.md#reset-a-forgotten-password) exactly. It removes only auth DB state while stopped and preserves TV/app/job state and ADB keys. Retrieve a generated token locally only when token setup is required; local loopback setup needs no token. Have the owner finish setup. **Done when** the owner confirms new login and preserved records; never relay the token.

For remote-access changes, consult [operations security settings](operations.md#security-controls-and-limits) before changing proxy, origin, cookie, or firewall configuration. **Done when** login is enabled and any changed route uses HTTPS, the exact public origin and secure cookies, authenticated access, and a private restricted network path.

## Handoff record

Report the host type and architecture; source revision; exact Compose project, ordered files, service, and volume; network mode and UI bind; login mode and whether auth data was preserved or a new account was set up (never credentials); build/start/health status; unprivileged UID/GID and volume-writability result; whether monitoring was initially paused for a new install or preserved for an existing instance; whether a TV was owner-paired and online; allowlisted apps and baseline confirmation or preserved existing state; and remaining limitations. Separate container health from real-TV reachability. Mark real-device compatibility and compile results unverified unless the owner explicitly ran and confirmed a device operation.
